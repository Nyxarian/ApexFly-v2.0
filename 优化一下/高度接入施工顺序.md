# 高度接入 · 开发顺序（施工顺序表）

## 排序规则（七条）

1. **先让"眼睛"准，再让"手"动** —— 估计器先做完、单独验证，再碰控制律；
2. **先搭骨架，再装肌肉** —— 模式状态机、门禁先落地，这个阶段**修正量恒 0**，零炸机风险就能验完最危险的那部分逻辑；
3. **先内环，后外环** —— 内环是唯一的阻尼来源，没有内环的外环必振荡；
4. **先安全，后首飞** —— 退出判据必须在第一次打开定高之前就位；
5. **先近端，后远端** —— 飞控跑通再改遥控器，避免两端同时动、出了问题分不清是谁；
6. **先验证，再整定** —— 每次改参数都必须有黑匣子波形作依据，不凭感觉连改；
7. ⭐ **模式只在地面切换**（2026-09-11 新增）—— 切换要求"**已上锁 + 杆在最低位**"，所以**一次飞行只能用一个模式**。
   这条顺带让"无扰切换"这件事基本消失（切换时两边油门都是最低）。
8. ⭐ **"停手"跟着骨架一起做**（2026-09-12 新增）—— 地面行为改由**停手状态机**负责（方案 §5.4）。它只依赖"高度读数 + 摇杆积分"，**不产生任何修正量**，
   所以放在 H6 阶段做是零炸机风险的；而且它**必须和门禁一起验证**，才能证明"地面不推杆就不动"。

## 台架仿真 / 静态检查（H6 起）

**飞控端**：在 PC 上把 `vertical_control.c` 单独编起来，用一个**假的估计器**喂高度，跑 17 个场景，
把验收矩阵在**烧录之前**先跑一遍；再用 `arm-none-eabi-gcc -fsyntax-only` 配桩头文件做类型检查。不碰任何硬件。

- 仿真脚本：`_inbox_会话提取/提取脚本/sim_vertical_control.c`（跑法见文件头注释，宿主机 gcc，两行命令）；
- ⭐ **H6 的"起飞保护"就是它抓出来的**：不加保护时，"推力偏弱、飞机离不了地"会变成
  "推杆 → 被按回停手 → 再推杆"的死循环，飞机永远起飞不了（详见方案 §15.3 第三个坑）；
- 结论：**17 个场景全过**。这类纯状态机逻辑都应该先跑仿真再上硬件，成本几乎为零。

**遥控端**（H17a 起）：遥控工程里带了**完整的 LVGL 与 CMSIS**，所以能直接用 `arm-none-eabi-gcc` 拿**真实头文件**
做语法检查，不必等 Keil：

```powershell
# 包含路径取自 CoreFly F2 Remoto.uvprojx 的 <IncludePath>；synchk 是本仓库里那版 GCC 兼容的 portmacro.h 桩
arm-none-eabi-gcc -fsyntax-only -std=gnu99 -Wall -Wextra -Wno-unused-parameter `
  -DUSE_HAL_DRIVER -DSTM32F407xx -DLV_LVGL_H_INCLUDE_SIMPLE -DLV_CONF_INCLUDE_SIMPLE `
  -I<synchk> -I<../Core/Inc> ...（其余见 uvprojx）... Algorithms/ui.c
```

⚠️ 唯一的坑：`Middlewares` 里只带了 **Keil(RVDS) 版 FreeRTOS port**，它的 `portmacro.h` 用 ARMCC 的
`__asm { }` 内联汇编，GCC 解析不了。所以本仓库里放了一份 **GCC 兼容的 `portmacro.h` 桩**
（`CoreFly F2 Remoto/.dsh-review-tmp/synchk/portmacro.h`，已 gitignore，**不参与 Keil 构建**），
把它放在包含路径**最前面**即可。H17a 就是靠这个在 PC 上查出了 `ui.c` 里一处漏改的 `.mode` 结构初始化。
