## 0. 先看结论

### 0.1 本阶段做什么 / 不做什么

| | 内容 |
|---|---|
| ✅ **做** | 串口接通 → 帧解析（**四重校验**）→ 质量门禁 → 有效性判定与冻结 → **零点标定** → 累积位移；全部**只打印** |
| ❌ **不做** | 位置环 / 速度环（OF6）、接进姿态环（OF11）、遥控端开关（OF10）、黑匣子字段（OF9）、按高度补偿增益的整定（OF12） |

⇒ **本阶段的风险等级是"零"**：不写电机、不写姿态、不改油门、不改定高。拆桨或不拆桨都一样。

### 0.2 三条最重要的发现（先看这三条）

**① ⭐⭐ 商家 demo 完全不看 `Quality`，也完全不做零点标定。**

这两条合起来正好解释了"光流定点会**恒速慢漂**"这个已知现象，见 §2.2 / §2.3。
⇒ **零点标定（OF5）不是可选优化，是定点能不能用的前提。**

**② ⭐ 供电只需 3.3V，而 GPS 座的 VCC 就是 3.3V ⇒ 直接把光流接到 GPS 座上即可。**

接线只要 **GND + TX 两根**（模块"只发不收"）。⚠️ 但**红黑千万不能接反，接反很可能烧模块**。

**③ ⭐ 本方案不需要动 CubeMX 的引脚配置，只需要改一行波特率。**

`USART2`（PA2/PA3）+ DMA1_Channel1 已经存在，GPS 就是挂在它上面的。把光流接到同一个座上，
**只是从 9600 改成 19200** —— 不需要新增任何外设、不需要重新分配引脚。
（接线和引脚都是现成的，这是这次能做到"零硬件改动"的原因。）

### 0.3 用户已拍板的决定（留档）

| # | 决定 | 内容 |
|---|---|---|
| 1 | 串口归属 | **编译期开关** `APEX_UART2_ROLE_FLOW`（1 = 光流 19200，0 = GPS 9600）。GPS 那条代码路径**照样编译、不删** |
| 2 | 日志时间戳 | **照原样显示，不做兜底**（见 §9） |
| 3 | 供电 | **沿用 GPS 座的 3.3V**（用户已确认该座是 3.3V，不需要额外取电方案） |
| 4 | 分两期走 | **第一期**：GPS 摘掉、光流接 GPS 座、打印口保持 115200；**第二期**（定点与定高都稳之后）：光流挪到打印口的 RX 脚、GPS 接回 USART2，做返航 |

## 1. 硬件事实（动手前必须认全，全部带出处）

### 1.1 帧格式与串口参数

| 项 | 值 | 出处 |
|---|---|---|
| 波特率 | **19200**，8 数据位，无校验，无流控 | 协议图 |
| 更新率 | 40ms 一帧 = **25Hz**，有数据自动发（不用轮询） | 协议图 |
| 帧长 | **9 字节固定** | 协议图 |

```
0xFE | 0x04 | DX_L | DX_H | DY_L | DY_H | SUM | Quality | 0xAA
 ↑     ↑      └──── 4 字节光流数据 ────┘    ↑       ↑        ↑
包头  长度                              累加和  图像质量   包尾
```

| 字节 | 含义 | 说明 |
|---|---|---|
| 0 | `0xFE` | 包头固定值 |
| 1 | `0x04` | 光流数据字节数（固定） |
| 2-3 | `DX_L` / `DX_H` | **int16 小端**：X 轴自上次更新的位移计数 |
| 4-5 | `DY_L` / `DY_H` | **int16 小端**：Y 轴同上 |
| 6 | `SUM` | **第 2~5 字节相加取低 8 位** |
| 7 | `Quality` | 0~100，**<30 建议舍弃** |
| 8 | `0xAA` | 包尾固定值 |

### 1.2 电气与接线

| 项 | 值 | 出处 |
|---|---|---|
| 线序 | **红 = VCC、黑 = GND、黄 = TX** | docx 教程 |
| ⚠️ **供电** | **2.7~3.3V，绝不能 5V**；**正负极千万不能接反，很可能烧坏模块** | docx 教程 |
| 官方措辞 | "Connect the sensor's **VDD (aka VCC or 3.3V)** to a 3.3V power source" | ArduPilot 官方页 |
| 接线方式 | **只接 GND + TX**（TX 接飞控的 RX，交叉通讯） | docx 教程 + ArduPilot 官方页 |
| 逻辑电平 | 3.3V（模块本身 3.3V 供电） | 由供电推出 |

且**核对线序**（GPS 座通常是 4 pin，光流是 3 线，错位可能把电供到信号线上）。

| 项 | 内容 | 出处 |
|---|---|---|
| 测量滞后 | **约 80ms**（= 2 帧） | ArduPilot 官方页：`EK2_FLOW_DELAY = 80` 是这款模块的推荐值 |

## 2. 商家 demo 逐行读后的发现

**来源**：`技术文档/mini光流资料/光流定点串级控制代码demo.rar`
（RAR4 压缩，用 Windows 自带 `tar.exe` = bsdtar/libarchive 解出；**原文是 GBK 编码**，
解出后转成 UTF-8 副本放在 `_inbox_会话提取/光流demo代码/`，正式留档建议移到 `技术文档/mini光流资料/demo代码/`。）

两个文件：`opticalflow_iic.c`（9002 字节）、`opticalflow_iic.h`（1493 字节）。
⚠️ **文件名写 `iic`，其实是串口版**（商家自己标错了，docx 教程也提到过）。

### 2.1 demo 做了什么（行号指解出的 UTF-8 副本）

| 环节 | 做法 | 行号 |
|---|---|---|
| 帧解析 | 只查 `buf[0] == 0xFE` 与累加和 | `:164, :166-167` |
| 取值 | `flow_x = buf[2] \| (buf[3]<<8)`（小端） | `:169-170` |
| 符号 | `speed_x = -flow_x; speed_y = -flow_y;`（**直接取反**） | `:172-173` |
| 高度补偿 | **7 档查表**：≤110→1.0、≤170→1.1、≤220→1.2、≤270→1.4、≤370→1.5、≤420→1.6、否则 1.7；**只放大 `kp`** | `:70-77` |
| 使能门禁 | 右摇杆在中位 **±30** 以内才使能 | `:82` |
| 累积 | `sum += v × 0.05f`（**写死 0.05s**），钳 ±50 | `:101-104` |
| 位置环 | **每 2 帧一次**（≈10Hz），**纯 P** 打累积流量到 0，`KKP=0.1`、`ki=0` | `:106-112`、`:40-42` |
| 速度环 | 靶 = 位置环输出，反馈 = 原始流量，`KP=12`、`KD=1` | `:125-126`、`:50-52` |
| 输出低通 | 一阶 **2.5Hz** | `:129-130` |
| 退出 | 杆偏离中心 ⇒ 输出清零 + **累积量与所有 PID 状态复位** | `:136-148` |

### 2.2 ⭐ 缺陷一：完全不看 `Quality`

`flow_decode()` 从头到尾**没有读过 `buf[7]`**，尽管协议图明确写着"**30 以下数据较差建议考虑舍弃**"。

**为什么这条致命**：光流镜头被挡、对着纯色地面/镜面/太暗时，模块很可能表现为
"**报 0 流量 + 低质量**"。只看流量的话，环路会把它读成"**飞机完全静止**"，
于是位置环什么都不做，而飞机照漂 —— **控制器以为自己钉住了，实际在飘。**

⇒ **我们的做法**：`Quality < 30` 直接判该帧无效 + **冻结**数据（OF3），绝不喂给环路。

### 2.3 ⭐⭐ 缺陷二：不做零点标定 ⇒ 这就是"恒速漂移"的根因

demo 是 `speed_x = -flow_x`，**没有减掉任何零点偏置**。

**为什么这条致命**（推导）：

- 位置环是**纯 P**（`ki = 0`），目标是 **0**，反馈是**累积流量**；
- ⇒ 环路稳定的条件是"**累积流量 = 0**"，也就是"**测到的流量累积为零**"；
- 如果静止时模块本来报 `+3 计数/帧`（像素噪声、光照不均、装配公差），
  那么环路为了让"测到的累积"回到 0，就必须让飞机**真的朝反方向匀速移动**；
- ⇒ **测量零偏 × 换算系数 = 恒定漂移速度。这就是"恒速漂移机"。**

⭐ **好消息：标定很简单**，而且我们已经有成熟模式可以照搬 ——
**IMU 水平零偏就是这么干的**：上电、静止时采几秒取平均，作为本场次的零点。

**不需要**转台、**不需要**已知位移的滑动测试、**不需要** counts-per-radian。

**代价（必须知道）**：得到的是"**把相对地面的运动压到零**"（= 钉住），
**不是**回到某个绝对坐标。长期仍有缓慢漂移 —— 这是光流的固有性质。

### 2.4 其它差异（我们比 demo 做得更细的地方）

| # | demo | 我们的做法 | 理由 |
|---|---|---|---|
| 1 | 只查校验和，**不查 `buf[1]==0x04`、不查 `buf[8]==0xAA`** | **四重校验**：`0xFE` + `0x04` + 累加和 + `0xAA` | 三重特征同时命中的误帧概率 ≈ 0；只查校验和时，一个 9 字节的随机窗口有 1/256 的概率通过 |
| 2 | 用**写死的 0.05s** 积分，而传感器是 40ms | **用真实 `dt`** | 帧率有抖动时会引入比例误差 |
| 3 | 高度补偿只放大 `kp`，且是 7 档查表 | 先把流量换算成**物理量**（乘高度），再谈增益 | 见 §8 的"待实测项 3" |
| 4 | 没有标定、没有质量门禁 | **都做** | §2.2 / §2.3 |
| 5 | 杆偏离中心时复位一切 | **照抄这个思路**（无扰切换） | 这是 demo 做得对的地方 |
| 6 | `LPF2pSetCutoffFreq(500,5)` 设了参数但**从没调用过 `LPF2pApply`** | 不抄这段死代码 | `:54`、`:249` |

### 2.5 抄什么 / 不抄什么

| 抄 | 不抄 |
|---|---|
| ⭐ 按高度调增益的**思路** | **具体 PID 参数**（`KKP=0.1`、`KP=12`、`KD=1`）—— 那是他们机架、他们量纲下的值 |

## 3. ① 当前情况会导致什么

**飞控里一行光流代码都没有**（`Modules/` 下无对应模块，全工程搜 `flow`/`PMW3901` 只命中 `overflow` 之类误报）。所以：

| 后果 | 说明 |
|---|---|
| **水平方向完全没有位置/速度反馈** | 起飞漂 2~5 米，之后持续缓慢漂走 —— 这是纯姿态控制的必然结果 |
| ⭐ **厂区面积小，漂移就直接撞** | 定高**没法长时间测试** —— 这正是要做定点的原因 |
| 而且**定高调好了也不会改善这一条** | "水平会漂"是缺少位置反馈的物理事实，不是定高的职责 |

## 4. ② 当前的解决办法（以及为什么不够）

**没有。** 现有的唯一水平信息是 IMU 的姿态角和磁航向 —— 它们回答"**机头朝哪、歪了多少**"，
**不回答"我在哪、我在往哪飘"**。姿态环把飞机调平了，但水平方向是纯开环。

不够的地方在于：**就算把姿态环调到完美，飞机也只是"平着飘"** —— 漂移方向由气流、
振动、安装误差、螺旋桨扭矩决定，没有一项被测量到。

⇒ 唯一的出路是**引入一个能看见地面的传感器**，这就是光流。

## 5. ③ 优化之后（本阶段的设计）

### 5.1 数据流

```
USART2 @19200（RX=PA3，DMA1_Ch1）
   │  ReceiveToIdle_DMA（照 gps.c 的成熟做法）
   ▼
环形缓冲（256B）
   │  flowTask 每 10ms 轮询一次，逐字节推进状态机
   ▼
帧同步 + 四重校验（0xFE / 0x04 / 累加和 / 0xAA）
   │  通过 ⇒ 取出 dx、dy、quality；不通过 ⇒ 丢弃并计数
   ▼
质量门禁：quality < 30 ⇒ 本帧作废（并计入 qrej）
   ▼
有效性判据：超时 / 连续低质量 / 高度超范围 ⇒ valid = 0 并【冻结】
   ▼
零点标定：静止采样期取平均 ⇒ 之后每帧减掉
   ▼
累积位移：sum += (dx - zero_x)（**直接累加计数，不乘 dt** —— 见 §5.5 的更正）
   ▼
输出 FlowState_t { dx, dy, quality, sum_x, sum_y, vx/vy, valid, cal, ... }
   ▼
【只打印】  ← 本阶段到此为止
```

### 5.2 帧解析（四重校验）

- 用**字节状态机**，不用"找 `0xFE` 再取 9 字节"的简单做法 —— 后者遇到半截帧/粘包会错位。
- 四重校验全过才算一帧：`buf[0]==0xFE`、`buf[1]==0x04`、`buf[6]==(buf[2]+buf[3]+buf[4]+buf[5])&0xFF`、`buf[8]==0xAA`。
- 校验失败时**只丢一字节**、重新同步（不要整帧丢弃后跳到第 9 字节，否则一次错位会连丢好几帧）。

### 5.3 有效性判据与冻结

| 判据 | 实现值（`flow.c`） | 说明 |
|---|---|---|
| 无有效帧超时 | `FLOW_TIMEOUT_MS = 200`（5 帧） | 25Hz 下连续丢 5 帧才算失效，容忍偶发丢帧 |
| 质量门禁 | `FLOW_CXOF_QUALITY_MIN = 30` | 协议图建议值 |
| 连续低质量 | `FLOW_QUALITY_BAD_MAX = 3`（约 120ms） | 用"连续几帧"而不是"单帧"：质量抖动是常态，单帧就失效会让下游每 40ms 抖一次 |
| 累积量钳位 | `FLOW_SUM_LIMIT_COUNTS = ±5000`（计数） | 防积分无界。⚠️ **占位值** —— 真实"1 计数 = 多少位移"没实测，OF6 算出尺度后重定 |
| 高度范围 | ⛔ **本阶段完全不实现** | **可信高度区间还没实测**（见 §8-1）。初稿写的是"先留常量、不设限"，实现时改成**连常量都不放** —— 一个 0~999 的死判据只会变成假安全感。等 OF4 实测之后再按真实区间写 |

**失效时的行为**：`valid = 0`，**冻结** dx/dy/sum（保持上一次），**不累积**。
（`quality` 本身**照常更新** —— 打印里要能看到"当前的"地面质量，而不是冻结前的旧值。）
⚠️ **不是清零** —— 清零会被下游误读成"飞机完全静止"，位置环于是什么都不做、而飞机照漂。
⚠️ 本阶段还没有 PID，所以"清 PID 状态"这条接口先留着，等 OF6 用。

### 5.4 零点标定

| 项 | 做法 |
|---|---|
| 触发 | ⭐ **上电即开始**（`Flow_Init()` 里直接进 `RUNNING`）<br>⚠️ **实现时对初稿的更正**：初稿写的是"上电后、**未解锁**、且数据有效时开始采样"。<br>实际**不看 `armed`** —— 那要给本模块新增一条跨模块依赖（`control_link`），而收益为零：<br>**上电那一刻飞机必然停在地面上**，这比"等解锁信号"更可靠；万一真的在动，下面的守卫会判失败并自动重来 |
| 采样长度 | `FLOW_CAL_FRAMES = 250`（约 10 秒 @25Hz）。2026-09-21 真机留样证明旧 25 帧窗口中单个 ±1 会产生 ±0.04 分数零点并制造长期漂移；250 帧把该影响降到 0.004 |
| 算法 | 对**原始每帧计数**取平均 ⇒ 作为零点偏置；之后每帧减掉 |
| ⚠️ 合理性守卫 | 若采样均值**超过 `FLOW_CAL_MAX_COUNT`（当前 **100** 计数/帧）** ⇒ 判定"当时没静止"、本次作废。<br>⚠️ **这是占位值**（真实零偏没实测过，见 §8-4）。宁可放宽也不要收紧 —— 太紧会把好标定判成失败。<br>理由：一个坏标定会变成**持续的漂移源**，比不标定更糟 |
| 失败后 | **1 秒（`FLOW_CAL_RETRY_MS`）后自动重来**，不需要重新上电。重试次数记在 `cal_attempts` 里（>1 说明失败过，值得看一眼） |
| 可观测 | `[OF]` 里打印 `cal=`（0 未开始 / 1 采样中 / 2 已完成 / 3 失败待重来）与 `z=`（标定得到的零点，v0.24 起打印 4 位小数） |
| 重标 | 换地面/换光照 ⇒ **重新上电**。<br>⚠️ 初稿提的那条 `ofc` 串口命令（不重新上电就重标）**本阶段没做** —— 验收要求本来就是"换地面重新上电"，多加一条命令要多碰一处解析器，不值得。真要做是几行代码 |
| ⭐ 标定期间**不累积** | 否则累积量里会混进一段"没减零点"的历史，事后减零点也擦不掉 |

### 5.5 累积位移、轴与符号

- ⭐ **`sum_x += (dx - zero_x)`，直接累加计数，不乘 dt**（实现时对初稿的更正）。
  依据：协议里 DX/DY 的定义是"**距上次更新以来的位移计数**"——它本身已经是一帧的位移量，
  不是速度；再乘一次帧间隔等于把时间权重算了两遍。
  （商家 demo 写的是 `sum += vx * 0.05f`，把每帧计数当成速度又乘了 0.05s；
  在恒定帧率下那只是差一个常数比例，方向不受影响，所以他们的定点也能跑；
  但帧率一有抖动，乘 dt 就会给慢帧额外权重，反而不准。）
- 另外输出 **`vx_cps` / `vy_cps`（计数/秒）= `(dx - zero_x) / dt_real`**，这是**速度环（OF6）**要的量。
  dt 不合理（同一毫秒内两帧，25Hz 下不该发生）时保持上一次的值。
- 两者都钳位；钳位值现在是**占位值**（真实"1 计数 = 多少位移"还没实测）。
- ⭐ **轴与符号必须实测**（OF4 的核心动作）：
  1. 飞机保持水平、**用手沿机头方向缓慢平移** ⇒ 看哪个轴**单调变化**、往哪边变；
  2. **反向平移** ⇒ 必须**反向变化**；
  3. 再测左右方向。
  ⇒ 这一步定死"模块 X/Y 轴 ↔ 飞机前后左右"以及**符号**。**不许照抄 demo 的取反。**

### 5.6 串口归属：编译期开关

```c
/* Core/Inc/apex_config.h（新增，手写、非 CubeMX 生成） */
#define APEX_UART2_ROLE_FLOW   1   /* 1 = 光流(19200)，0 = GPS(9600) */
```

| ⭐ **不需要动 CubeMX 引脚配置** | USART2 + PA2/PA3 + DMA1_Ch1 全是现成的，**只改一行波特率** |
| 失败模式少 | 比"上电自动识别"少一个失败点（插头松了会静默退回 GPS） |

### 5.7 打印格式

新增一行 `[OF]`，与 `[V]` 同节奏（`TOF_PRINT_PERIOD_MS = 500`，在 `tofTask` 里打印，低优先级、不在控制环里）：

```
[OF] n=<帧数> bad=<累加和>/<格式> qrej=<质量拒绝> | q=<质量> dx=<计数> dy=<计数> | z=<零点x>,<零点y> | sx=<累积x> sy=<累积y> | v=<0|1> cal=<0-3> a=<age_ms>
```

- `n` 持续增长 ⇒ 帧在进来；`bad` 长期增长 ⇒ 波特率/接线有问题；
- `q` 是我们判断"地面纹理/光照行不行"的唯一依据；
- `z` 与 `sx/sy` 是 OF5 的核心观测量；
- `v` 与 `cal` 是状态位。

⚠️ 新行约 100 字符 / 500ms，加在 `[V]`（约 150 字符）之后，**总带宽仍远低于 115200**。

### 6.6 停止条件（出现任一条立刻停手并回来）

1. **插之前量到的不是 3.3V** ⇒ 先断电，不许插；
2. `q` 长期 < 30 或帧率远低于 25Hz ⇒ **接线/波特率/供电有问题，不要继续往下做**；
3. 静止时 `sx/sy` **持续单向快速增长** ⇒ 标定没生效；
4. 平移测试的**方向与机头完全对不上** ⇒ 轴映射写错；
5. 普通模式或定高模式出现**任何**与改动前不同的现象。

### 6.7 软件自查（烧录前，不用硬件）

照 H8~H14 的做法写一个**宿主机仿真**，喂**合成字节流**：

| 用例 | 期望 |
|---|---|
| 正常帧流 | 帧数正确、dx/dy 还原正确、`q` 正确 |
| 坏校验和的帧 | 被拒、计入 `bad` |
| `buf[1] != 0x04` | 被拒 |
| `buf[8] != 0xAA` | 被拒 |
| **半截帧**（只有前 5 字节） | 不误判、等待后续字节 |
| **粘包**（两帧连在一起） | 两帧都正确解出 |
| **帧中间插入噪声字节** | 能重新同步，后续帧不丢 |
| `q = 0` / `q = 200`（越界） | 前者拒绝、后者按上限处理（不越界） |
| 连续失帧 5 帧 | `v` 变 0、数据冻结；恢复后 `v` 回 1 |
| 标定期间故意喂大流量 | 标定**失败**（守卫生效） |

⚠️ **仿真不能代替真机验证**。它能证明解析与状态机的逻辑；证明不了"模块真的在发、
Quality 真实水平、地面纹理行不行"。

| 5 | **厂区地面的纹理/光照够不够** | OF2/OF3 实测 | `q` 是唯一依据；不够就得铺纹理或换场地 |
| 6 | **手头模块是新款还是老款** | 用户看一眼 | 影响安装方向的参考图（老款/新款不同） |

**关于第 3 条（值得单独说）**：

ArduPilot/商家的做法是**按高度放大增益**（demo 是 7 档查表：110→1.0 一路到 420→1.7）。
物理上，光流计数 ∝ 位移 ÷ 高度，所以**要还原成位移就必须乘高度** ⇒ 正确补偿应当 **∝ 高度**。

但 demo 的表只从 1.0 涨到 1.7，而高度涨了约 3.8 倍 ⇒ **它只补了一半左右**（保守）。

⇒ **我们不照抄那张表**，而是在 OF12 用实测数据决定：是先乘高度换算成物理速度、
还是保持流量量纲再调增益。**本阶段先不碰这个。**
