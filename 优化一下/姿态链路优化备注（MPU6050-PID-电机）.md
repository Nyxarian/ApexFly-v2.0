MPU6050 底层六轴读取 → 零偏/水平零点校准 → 姿态解算 → 串级 PID → 混控 → 电机的**全部流程**，并找出可优化空间（任务调度、数据处理、算法实现）。

## 4. R1 根因详解与修订版

> R1 在《ApexFly V2.0 悬停稳定性分析与定高定点返航实施方案.md》中的原始定义：
> "实际增益配置 = 纯 P 角度环、无阻尼内环、无偏航控制 → 系统欠阻尼/低刚度，大风下姿态发散"（★★★★★）

### 4.1 原始论据（基于 8/23 及更早数据）

- 编译默认 `kDefaultPidParams` 六组增益**全为 0**；
- 黑匣子 8/23 的 5 个场次：内环全 0、外环 Kp 0.3/1.0、无 Ki/Kd、偏航全 0；
- `attitude_control.c` 有"内环全 0 时外环输出直通当微秒用"的旁路（`AttitudeControl_InnerEnabled`）。

**该论据对 8/23 及更早成立；对 8/29 之后（内环已开 1.30）不成立。**

### 4.2 修订版 R1'：今天这套配置下，仍然成立的四个机制

#### 论据 1（仍成立）：横滚/俯仰 **Ki = 0 → 没有积分，抗风静差消不掉**

大风的本质是**方向恒定的持续推力**。只有 P（加少量 Kd）时，对抗常值力矩必然留下**稳态倾角**（风把机体吹到某个角度，该角度产生的差速刚好抵消风矩）。这个倾角消不掉，而倾角一存在，推力就有水平分量 → 飞机持续朝一个方向加速 → **单向漂移**。
8/29 实测佐证：即便内环已开，阵风下姿态峰值仍到 48°、角速度峰值 328°/s。

#### 论据 2（新，最关键）：**偏航参数为 0 → 偏航完全无控，且存在"杆量直通"隐藏路径**

代码位置 `attitude_control.c:126-170`：

```c
if (stick_deflected)                       // |yaw_stick| > 80
{
    rate_limit_dps = yaw_cascade.outer.out_max;          // = 200（限幅参数）
    stick_rate_dps = (yaw_stick / 1000.0f) * rate_limit_dps;   // 最大 ±200
    yaw_cascade.inner_setpoint = stick_rate_dps;
    if (AttitudeControl_InnerEnabled(&yaw_cascade))
        inner_out = CascadePid_UpdateInner(...);          // 正常：PID 输出
    else
        inner_out = stick_rate_dps;                       // ← 内环为 0 时：杆量数值直接当微秒
    return inner_out;
}
```

即：**yaw_rate 的 Kp/Ki/Kd 全为 0 时，偏航杆量被直接当作混控修正微秒打进混控**，满杆 = **±200us** 的偏航差速（两个电机 +200、两个 −200），足以瞬间把机头拧起来并造成推力严重失衡。

| 触发场景 | 后果 | 如何确认 |
|---|---|---|
| 飞行中手碰偏航杆（含手抖） | 瞬时大偏航差速 → 急转/翻滚 | 黑匣子 `yaw_corr` 列是否出现非 0 大值 |
| **遥控器偏航通道中位未对准**（读数超出 ±80 死区，例如中位 100） | 持续输出约 ±20us 偏航差速 → **缓慢持续自旋**；且每拍 `Pid_Reset` + `yaw_hold_valid=false`，**航向锁定永久失效** | 解锁后松杆，看串口/黑匣子里偏航杆量是否为 0 |
| 遥控器摇杆标定偏差 | 同上，姿态环持续"追"旋转中的机体 | 同上 |

#### 论据 3（仍成立）：偏航无阻尼 → 机头自由转 → 横滚/俯仰被持续激励

即使偏航杆在中位（yaw_corr=0），偏航通道也是空转的：四电机反扭矩不平衡无人管，风一吹就"风标效应"转向。机头一转，横滚/俯仰环的"水平"在惯性系里就在变，等于给一个阻尼偏弱的系统持续注入新扰动 → 表现为震荡。
8/29 场次 1738 当时至少还有 `yaw_rate = 1.0` 的阻尼；今天连这个都没有。

#### 论据 4（新）：节拍恶化（今天固件多了 6ms/拍打印）

对"阻尼偏弱 + 无积分"的系统，等效相位延迟增加会把"能收敛"变成"来回摆"。可用今天黑匣子的 `t_ms` 直接证实或排除。

## 5. 磁力计到底有没有进 PID

### 5.1 三层对照

## 6. 全链路审计：MPU6050 → PID → 电机

### 6.0 三个"硬约束级"发现（比调 PID 更重要）

#### 发现 1：控制环名义 100Hz，但**电机实际每 20ms 才收到一次新脉宽**

证据链：
- `tim.c:100-102`：TIM8 `Prescaler=169`、`Period=19999` → 1MHz 计数、**周期 20ms（50Hz）**；
- **关键**：`stm32g4xx_hal_tim.c:4358` —— HAL 在 PWM 模式下自动置 `TIM_CCMR1_OC1PE`（输出比较**预装载**）；
- 因此 `__HAL_TIM_SET_COMPARE()` 写入 CCR 的值，要等**下一个更新事件（20ms 后）**才装载到影子寄存器；
- 结果：控制环 10ms 算一次写一次，但电机看到的脉宽**每 20ms 变一次**，平均延迟 10ms、最坏 20ms。

**后果**：姿态环相位裕度被这一项吃掉一大半；闭环带宽被 50Hz 更新率限制在几 Hz，大风抗扰能力上不去。

**优化**：TIM8 改 **400Hz**（Period=2500 @1MHz，分辨率仍 1us），延迟 10ms→1.25ms；或用电调支持的 OneShot125/DShot。**需先确认电调支持 400Hz**。

#### 发现 2：今天固件控制环每拍被串口打印阻塞 ~6ms

`motor_test.c:236`（9/3 新增、9/8 编译进固件）：每拍 `Debug_Printf` 一行 ~70 字节 @115200 ≈ 6ms 阻塞，且发生在姿态解算**之前**。
- 8/29（无此行）：`t_ms` 中位数 10ms；
- 今天（有此行）：理论周期 10.5+6 ≈ 16.5ms 且抖动。

#### 发现 3：混控之后又强制每路 ≥1050us，破坏差速平衡

`mixer.c` 已做正确的饱和保护（`Mixer_UpdateScale` 按四路中最先撞限的一路统一缩放修正，保证力矩方向不变形），但 `motor_test.c:58-61` 的 `MotorTest_ApplyMixer()` 又**逐路硬抬到 1050us**：

```c
if (output->motor_1_us < 1050) output->motor_1_us = 1050;   // 四路都这样
```

一旦某一路本该 950us 被抬到 1050 → 四路差速关系被破坏、力矩方向被扭曲。且混控下限（1000us）与此处（1050us）不一致。
**正确做法**：把"最低有效油门"作为统一参数传进 `Mixer_Calculate()`，参与 `correction_scale` 计算，而不是事后逐路裁剪。

### 6.2 B. 传感器数据层（MPU6050）

| 环节 | 现状 | 问题 | 优化空间 |
|---|---|---|---|
| 量程 | 陀螺 ±2000dps（16.4 LSB/dps）、加计 ±8g（4096 LSB/g） | 实际角速度 <500dps，大量程 = 更大噪声 + 更低分辨率 | 陀螺改 ±500dps（65.5 LSB/dps，噪声约降 4 倍）、加计改 ±4g；注意抗冲击余量 |

| 采样率 | `SMPLRT_DIV=0` → 内部 1kHz | 以 100Hz 读 = 抽点，且**不检查 Data-Ready** | 保留 1kHz，改由 DRDY 中断触发读取 |
| 读取原子性 | 一次连续读 14 字节（~0.4ms @400kHz） | 内部 1ms 更新 → 约 40% 概率**跨更新边界**，accel 与 gyro 差最多 1ms | 读前查 `INT_STATUS.DATA_RDY`，或启用 FIFO 批量读 |
| 温度 | 读了 `temperature_c` 但**从未使用** | 陀螺零偏温漂典型 ±0.05°/s/℃；自热 10–20℃ → 漂移 0.5–1°/s | 温度-零偏一阶补偿（需标定），或静止自适应零偏 |
| 加计校准 | **没有做**（只有"水平零点"） | 加计零偏几十 mg → 静态姿态误差 1–2°，且随姿态变化 | 六面法标定零偏+尺度，存 Flash |
| 陀螺零偏采集 | 上电 200 拍（2s）平均，**无静止检测、无方差检查、无温度稳定等待** | 开机 2s 内芯片自热未稳；有振动/风吹则零偏带误差 | 延长到 5–10s；加"陀螺方差 < 阈值 + 加计模长≈1g"双重门禁 |
| 水平零点采集 | 静置 200 拍取 roll/pitch 平均后**直接相减**（`imu_level.c`） | ① 同时吸收安装倾角与姿态估计静态误差；② **若采集时机体不在真实水平（起落架不平/斜面），就变成永久目标角偏置 → 固定倾角飞行 → 单向漂移**；③ 无水平性/方差检查；④ 只存 RAM，每次开机重采 → 每次飞行不一致 | 改为"用加计重力方向标定安装倾角 + 加计零偏"并**存 Flash**；采集准入条件用"加计模长≈1g + gyro 静止 + 倾角变化 < 阈值"；台架用水平仪交叉验证 |
| I2C 速率 | 400kHz（`Timing=0x40B285C2`） | 14B 读 ≈0.4ms + HAL 开销，占 10ms 周期 5–10% | 改 DMA 读（配合 DRDY 中断），CPU 占用近 0 |

### 6.3 C. 姿态解算层（Mahony）

| 环节 | 现状 | 问题 | 优化空间 |
|---|---|---|---|
| 积分方法 | **一阶欧拉**：`q += 0.5*q⊗ω*dt` | dt=10ms、ω=300°/s 时每拍转 3°，误差随 ω²dt 增长；dt 抖动时不稳定 | 改**中值积分**（ω_prev 与 ω_now 平均）或四元数指数映射，代价极小、精度显著提升 |

| 初始化 | 首拍用加速度算 roll/pitch 置初值 | 首拍有振动/机动则初值偏 | 用零偏采集期间的平均加速度作初值 |

### 6.4 D. 控制算法层（串级 PID）

| 环节 | 现状 | 问题 | 优化空间 |
|---|---|---|---|
| 结构 | 外环角度→目标角速度，内环角速度→us | 设计正确 | 保持 |
| 内环旁路 | **内环 Kp/Ki/Kd 全 0 时外环输出直通当 us**（`attitude_control.c:70-73,117-121`） | 危险后门：参数丢失时静默退化为"无阻尼角度环"（8/23 及之前正是此状态） | 加"内环未启用 → 拒绝解锁/告警"门禁，或删除旁路 |
| 微分项 | `deriv = (error - last_error)/dt`，**作用在误差上**，无低通 | ① 打杆/Trim 变化 → **微分冲击**；② 陀螺噪声被 Kd 放大 | 改为对**测量**微分 + 一阶低通 |

| 输出限幅 | 三轴修正 ±200us，与基础油门无关 | 低油门（1100us）时 200us 相对过大，靠混控 scale 兜底；而 `MotorTest_ApplyMixer` 的 1050 下限又破坏 scale（发现 3） | 让"最低有效油门"进混控统一计算；或按油门比例限制修正 |
| 目标角速率限制 | 杆量直接映射目标角（满杆 10°），无斜率限制 | 杆量跳变 → 目标角跳变 → 误差跳变 → 冲击 | 加目标角一阶滤波/速率限制 |
| 限幅语义 | `..._MAX_RATE_DPS` 同时当外环 out_max 和 i_limit；`..._MAX_CORRECTION_US` 同理 | 语义耦合，调参易误伤 | 拆成独立参数 |
| dt 使用 | `control_dt_s` 被限幅到 [5ms, 30ms] | 与真实周期不一致时积分有偏 | 用微秒真实 dt，只做异常保护 |
| 电压补偿 | 无 | 12.6V→11.0V 时同脉宽推力降约 10% → 悬停漂移 | 用 `battery.c` 电压做一阶推力补偿 |

### 6.6 延迟链估算（对姿态环相位滞后）

| 环节 | 延迟 |
|---|---|
| MPU6050 DLPF（CONFIG=3） | 约 4.9ms |
| I2C 读 14 字节 @400kHz | 约 0.4ms |
| 任务调度抖动 | 0–1ms（tick 粒度）+ 被 radio 抢占 |
| 姿态解算 + 控制计算 | <0.1ms（硬件 FPU） |
| **PWM 预装载等待** | **0–20ms（平均 10ms）** ← 最大项 |
| 电机 + 螺旋桨响应 | 20–50ms（物理一阶时间常数） |
| **合计** | **约 35–75ms** |

→ 这解释了为什么"姿态环带宽只能做到几 Hz"：相位滞后主要来自 PWM 更新与执行机构，而不是 PID 本身。

### 6.7 附带澄清：FPU 上下文不是问题

审计中一度怀疑 `FreeRTOSConfig.h` 的 `configENABLE_FPU 0` 与工程 `<Cpu>...FPU2</Cpu>` + map 中 `__hardfp_*`（硬件浮点）冲突。核实结论：

- `Middlewares/.../portable/RVDS/ARM_CM4F/port.c:36-38` 强制要求 `__TARGET_FPU_VFP`（即必须启用硬件浮点）；
- `xPortStartScheduler()` 调用 `prvEnableVFP()` 使能 CPACR；
- `xPortPendSVHandler()` 中 `tst r14,#0x10` → 任务使用 FPU 时 `vstm/vldm {s16-s31}` 保存/恢复高 16 个 FPU 寄存器；S0–S15/FPSCR 由硬件 lazy stacking 处理；
- 该 port.c 版本**未引用** `configENABLE_FPU`，所以该宏为 0 不影响 FPU 上下文保存。

→ **结论：FPU 上下文保存是正确实现的，不是 BUG**（此项可排除）。
